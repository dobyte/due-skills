# 绑定网关

## 概述

绑定网关（Bind Gate）是用户登录流程中的关键步骤，用于建立用户（UID）与网关连接（Gate Connection）的关联关系。只有完成绑定，网关才能将用户的消息正确路由到节点服，并将节点服的响应转发给用户。

## 核心概念

### 三元组关系

```
┌─────────┐         ┌─────────┐         ┌─────────┐
│   UID   │ ←────── │  Gate   │ ←────── │  Conn   │
│ 用户 ID │  绑定    │ 网关服  │  连接    │ 连接 ID │
└─────────┘         └─────────┘         └─────────┘
     ↑                                     ↑
     │                                     │
   业务层标识                           网络层标识
```

- **UID（User ID）**：用户唯一标识，由业务层生成
- **Gate**：网关服实例，维护连接池
- **Conn（Connection ID）**：连接标识，由网关服分配

### 绑定信息

绑定关系分为两层：

- **定位层（Redis）**：由定位器（如 redis 定位器）持久化 UID 与 GID 的映射，使用字符串键存储：

```
{prefix}:locate:user:{uid}:gate   # 值为网关服实例 ID（GID），prefix 默认为 due:locate
```

- **会话层（网关内存）**：网关服在内存 session 中保存 CID 与 UID 的映射（User 会话），用于把消息转发到具体连接；连接断开时随会话一并移除。

## 绑定流程

### 完整登录流程

```
1. 客户端建立 TCP/WebSocket 连接
   ↓
2. 网关服分配 Connection ID（临时连接，未绑定用户）
   ↓
3. 客户端发送登录请求（route=1, 携带账号密码）
   ↓
4. 网关服将消息转发到节点服（无状态路由）
   ↓
5. 节点服验证账号密码
   ↓
6. 验证成功，生成 UID
   ↓
7. 节点服调用 ctx.BindGate(uid) 绑定网关
   ↓
8. 节点服通过 RPC 请求网关服执行绑定：网关服在内存会话中绑定 CID↔UID，并将 UID→GID 写入 Redis（定位器），随后触发 Reconnect 事件
   ↓
9. 节点服返回登录成功响应
   ↓
10. 节点服按 UID→GID 将响应发送到网关服，网关服再按 CID 转发给客户端
```

### 代码示例

```go
// 登录处理器（无状态路由）
func loginHandler(ctx node.Context) {
    req := &loginReq{}
    if err := ctx.Parse(req); err != nil {
        ctx.Response(&loginRes{Code: 400, Message: "参数错误"})
        return
    }
    
    // 1. 验证账号密码
    uid, err := verifyUser(req.Account, req.Password)
    if err != nil {
        ctx.Response(&loginRes{Code: 401, Message: "账号或密码错误"})
        return
    }
    
    // 2. 绑定网关（关键步骤）
    if err := ctx.BindGate(uid); err != nil {
        log.Errorf("绑定网关失败: uid=%d, err=%v", uid, err)
        ctx.Response(&loginRes{Code: 500, Message: "服务器内部错误"})
        return
    }
    
    // 3. 绑定节点（如果是有状态服务）
    if err := ctx.BindNode(uid); err != nil {
        log.Errorf("绑定节点失败: uid=%d, err=%v", uid, err)
        ctx.UnbindGate(uid)  // 回滚网关绑定
        ctx.Response(&loginRes{Code: 500, Message: "服务器内部错误"})
        return
    }
    
    // 4. 初始化玩家数据
    if err := initPlayerData(uid); err != nil {
        log.Errorf("初始化玩家数据失败: uid=%d, err=%v", uid, err)
        ctx.UnbindNode(uid)
        ctx.UnbindGate(uid)
        ctx.Response(&loginRes{Code: 500, Message: "服务器内部错误"})
        return
    }
    
    // 5. 返回登录成功
    ctx.Response(&loginRes{
        Code:    0,
        Message: "登录成功",
        UID:     uid,
    })
}
```

## 绑定机制详解

### BindGate 方法

```go
// 方法签名（node.Context 接口）
BindGate(uid ...int64) error
```

**参数：**
- `uid`（可选）：用户 ID。不传时使用当前上下文已关联的 UID。

**返回值：**
- `error`：绑定失败时返回错误；当消息并非来自网关（GID 为空）且未携带 UID 时，返回 `errors.ErrIllegalOperation`。

**调用链：**

```
ctx.BindGate(uid)                               // request / event 实现
  → node.Proxy.BindGate(ctx, gid, cid, uid)     // 使用当前上下文的来源网关与连接
    → GateLinker.BindGate(ctx, gid, cid, uid)   // 构建到该网关的 RPC 客户端
      → 网关 provider.Bind(ctx, cid, uid)
        → Session.Bind(cid, uid)                // 内存：绑定 CID↔UID（若 UID 已绑定旧连接则强制关闭旧连接）
        → proxy.bindGate(ctx, cid, uid)
          → Locator.BindGate(ctx, uid, gid)     // Redis：写入 UID→GID
          → 触发 Reconnect 事件
```

成功绑定后，上下文中的 UID 会被更新为传入的 UID。

### 重复登录（顶号）

当同一 UID 在另一条连接上再次绑定时，网关服的会话层会关闭旧连接并用新连接替换，从而实现“顶号”：

```
用户 A 在连接 Conn-100 登录并绑定 UID=1001（Gate-1）
    ↓
用户 A 在另一条连接 Conn-200 再次登录并调用 BindGate(1001)
    ↓
Gate-1 执行 Session.Bind(Conn-200, 1001)
    ↓
检测到 UID=1001 已绑定 Conn-100 → 强制关闭 Conn-100
    ↓
更新会话映射：UID=1001 → Conn-200，并写入 Redis：UID=1001 → Gate-1
    ↓
触发 Reconnect 事件
```

该行为由网关服的会话层实现，节点服无需显式发送“踢下线”请求。

## 解绑网关

### 自动解绑

连接断开时，网关服自动解绑：

```
网关服 handleDisconnect(conn)
    ↓
Session.RemConn(conn) 确认会话存在并移除
    ↓
若 conn.UID() != 0：调用 proxy.unbindGate(ctx, cid, uid)
    ↓
Locator.UnbindGate(ctx, uid, gid)   // 从 Redis 删除 UID→GID（校验 GID 一致才删除）
    ↓
触发 Disconnect 事件
```

### 手动解绑

节点服可以主动解绑：

```go
// 登出处理器
func logoutHandler(ctx node.Context) {
    uid := ctx.UID()
    
    // 保存玩家数据
    savePlayerData(uid)
    
    // 解绑节点
    ctx.UnbindNode(uid)
    
    // 解绑网关
    ctx.UnbindGate(uid)
    
    ctx.Response(&logoutRes{Code: 0})
}
```

## 绑定信息查询

### 查询用户所在网关

节点服可通过代理查询用户绑定的网关：

```go
// 查询用户所在网关（返回 GID）
func queryUserLocation(ctx node.Context, uid int64) {
    gid, err := ctx.Proxy().LocateGate(ctx.Context(), uid)
    if err != nil {
        log.Errorf("查询用户位置失败: uid=%d, err=%v", uid, err)
        return
    }

    log.Printf("用户 %d 在网关 %s", uid, gid)
}

// 判断用户是否在指定网关上（返回该用户实际所在网关、是否命中、错误）
gid, on, err := ctx.Proxy().AskGate(ctx.Context(), "gate-id", uid)
```

### 判断用户是否在线

```go
func isUserOnline(ctx node.Context, uid int64) bool {
    gid, err := ctx.Proxy().LocateGate(ctx.Context(), uid)
    if err != nil || gid == "" {
        return false
    }

    online, err := ctx.Proxy().IsOnline(ctx.Context(), &cluster.IsOnlineArgs{
        Kind:   session.User,
        GID:    gid,
        Target: uid,
    })

    return err == nil && online
}
```

## 消息转发机制

### 客户端 → 节点服

```
客户端发送消息（route=10, data={...}）
    ↓
网关服接收消息
    ↓
网关服查询连接绑定信息：Conn-100 → UID=1001
    ↓
网关服构造内部消息：{UID: 1001, Route: 10, Data: {...}}
    ↓
网关服根据路由号查询节点服（无状态/有状态路由）
    ↓
网关服通过 RPC 转发消息到节点服
    ↓
节点服处理消息
```

### 节点服 → 客户端

```
节点服发送消息（UID=1001, route=10, data={...}）
    ↓
节点服查询用户所在网关：UID=1001 → Gate-1
    ↓
节点服通过 RPC 将消息推送到 Gate-1（Kind=User, Target=1001）
    ↓
Gate-1 在会话中查找 UID=1001 对应的连接：Conn-100
    ↓
Gate-1 将消息转发给客户端
```

## 最佳实践

### 1. 绑定顺序

```go
// ✅ 正确顺序：先绑定网关，再绑定节点
ctx.BindGate(uid)
ctx.BindNode(uid)

// ❌ 错误顺序：先绑定节点，再绑定网关
ctx.BindNode(uid)  // 此时 UID 还未绑定网关，无法接收消息
ctx.BindGate(uid)
```

### 2. 错误处理与回滚

```go
func loginHandler(ctx node.Context) {
    uid := generateUID()
    
    // 绑定网关
    if err := ctx.BindGate(uid); err != nil {
        ctx.Response(&loginRes{Code: 500})
        return
    }
    
    // 绑定节点
    if err := ctx.BindNode(uid); err != nil {
        ctx.UnbindGate(uid)  // 回滚网关绑定
        ctx.Response(&loginRes{Code: 500})
        return
    }
    
    // 初始化数据
    if err := initPlayerData(uid); err != nil {
        ctx.UnbindNode(uid)  // 回滚节点绑定
        ctx.UnbindGate(uid)  // 回滚网关绑定
        ctx.Response(&loginRes{Code: 500})
        return
    }
    
    ctx.Response(&loginRes{Code: 0})
}
```

### 3. 防止重复登录

```go
func loginHandler(ctx node.Context) {
    // 检查当前连接是否已绑定
    if ctx.UID() != 0 {
        ctx.Response(&loginRes{Code: 400, Message: "已登录"})
        return
    }
    
    // ... 登录逻辑 ...
}
```

### 4. 心跳检测与自动解绑

```toml
# 网关服网络配置
[network.tcp.server]
  # 心跳检测间隔，0 表示不启用
  heartbeatInterval = "10s"
  # 心跳机制：resp（响应式心跳）| tick（定时主推心跳）
  heartbeatMechanism = "resp"
```

连接因心跳超时被断开后，由网关服的断开回调自动解绑网关（见“自动解绑”一节）。

## 常见问题

### Q1: 绑定网关失败怎么办？

**A:** 常见原因：
- CID 或 UID 非法（<= 0），网关返回 `errors.ErrInvalidArgument`
- 连接不存在（会话未找到），网关返回 `errors.ErrNotFoundSession`
- 消息并非来自网关（GID 为空）且未携带 UID，节点返回 `errors.ErrIllegalOperation`
- 网关已关闭或本地定位器/Redis 连接失败

检查日志和 Redis 状态。

### Q2: 用户登录后收不到消息？

**A:** 可能原因：
- 未绑定网关
- 绑定信息未同步到 Redis
- 网关服与节点服 RPC 连接失败

使用 `ctx.Proxy().LocateGate(ctx.Context(), uid)` 检查用户所在网关。

### Q3: 如何实现多设备同时在线？

**A:** 默认情况下，同一 UID 在网关会话中只对应一条连接，新连接绑定会强制关闭旧连接（顶号），且定位器中 UID→GID 只保留最新值。如需支持多设备，需要改造网关会话与定位器的绑定语义（例如按设备维度区分 UID）。

### Q4: 绑定信息丢失怎么办？

**A:** 绑定信息存储在 Redis 中，定位器写入时未设置过期时间（键无 TTL）。如果 Redis 数据丢失：
- 用户需要重新登录
- 建议在 Redis 中启用持久化（RDB/AOF）

## 总结

绑定网关是用户登录流程的核心环节，通过建立 UID 与网关连接的关联，实现了消息的正确路由。理解绑定机制，是开发稳定可靠的游戏服务器的基础。
