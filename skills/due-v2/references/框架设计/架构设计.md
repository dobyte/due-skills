# 架构设计

## 概述

Due v2 采用分层架构设计，把游戏服务器拆分为若干职责明确、松耦合的组件，支持灵活部署与水平扩展。框架围绕**网关服（Gate）**、**节点服（Node）**、**网格服（Mesh）**三类集群实例展开（`cluster.Kind` 还预留了 `Master` 类型）。

## 核心组件

### 1. 网关服（Gate）

**职责：**

- 维护客户端长连接（TCP / WebSocket / KCP / QUIC）
- 处理心跳检测与连接保活
- 按路由号把客户端消息分发/转发到节点服（无状态路由按策略分发，有状态路由按用户绑定定位）
- 协议编解码

**特点：**

- 无状态设计，可水平扩展
- 不提供业务开发接口，专注连接管理与消息转发
- 通过 `cluster/gate` 组件实现，路由分发策略由 `etc.cluster.gate.dispatch` 配置

### 2. 节点服（Node）

**职责：**

- 承载游戏业务逻辑，注册并处理路由消息（`RouteHandler`）
- 处理有状态路由消息
- 管理用户会话与游戏数据
- 支持事件处理、Hook 生命周期、Actor 模型与微服务 Provider

**特点：**

- 有状态服务，可与用户（UID）绑定
- 支持单线程、多协程、Actor 三种并发模型
- 通过注册中心实现服务发现，通过 locator 记录用户绑定

### 3. 网格服（Mesh）

**职责：**

- 承载无状态微服务
- 通过 transporter（gRPC / RPCX）对外提供 RPC 服务
- 供节点服/其他服务通过 `NewMeshClient` 调用

**特点：**

- 无状态设计，便于独立更新
- 必须注册至少一个 service provider，否则启动终止
- 通过注册中心发布服务实例（`Services` 字段）

### 集群实例状态

任一集群实例都遵循统一的状态机（`cluster.State`）：

| 状态 | 说明 |
|------|------|
| `Shut` | 已关闭，不可访问（未启动或已销毁） |
| `Work` | 健康，可分配更多用户 |
| `Busy` | 资源紧张，不再接收更多用户 |
| `Hang` | 即将下线，正在回收资源（关闭中） |

`SetState` 只能在 `Work` 与 `Busy` 之间切换；执行 `Close` 会进入 `Hang`，`Destroy` 会进入 `Shut`。

## 架构分层

```
┌─────────────────────────────────────────┐
│           客户端层 (Client)              │
└─────────────────────────────────────────┘
                  ↓
┌─────────────────────────────────────────┐
│         网关层 (Gate Cluster)            │
│  - 连接管理、协议编解码、消息路由          │
└─────────────────────────────────────────┘
                  ↓
┌─────────────────────────────────────────┐
│         业务层 (Node Cluster)            │
│  - 游戏逻辑、状态管理、Actor 模型         │
└─────────────────────────────────────────┘
                  ↓
┌─────────────────────────────────────────┐
│         服务层 (Mesh Cluster)            │
│  - 无状态微服务、跨节点通信               │
└─────────────────────────────────────────┘
                  ↓
┌─────────────────────────────────────────┐
│       基础设施层 (Infrastructure)        │
│  - 注册中心、配置中心、缓存、数据库        │
└─────────────────────────────────────────┘
```

组件之间通过内部 RPC 链路（linker）与集群消息协议通信；网关与节点之间、节点与节点之间均使用内置的 linker client/server。

## 核心设计理念

### 1. 高内聚低耦合

- 各组件职责单一，边界清晰
- 通过接口、注册中心与内部协议通信，避免直接依赖
- 支持独立部署与升级

### 2. 模块化设计

- 网络、编解码、注册中心、定位、缓存、锁、日志等均可按需替换（接口 + 注册 + 选项）
- 统一接口规范，便于替换实现（如 `encoding.Codec`、`locate.Locator`、`registry.Registry`、`crypto.Encryptor`）

### 3. 分布式友好

- 内置服务注册与发现（Consul / Etcd / Nacos / Polaris）
- 通过 locator 记录用户与网关/节点的绑定关系，支持跨节点消息路由

### 4. 灵活的并发模型

- **单线程模型**：节点由一个分发协程顺序消费任务、路由与事件队列，适合需要顺序执行的场景
- **多协程模型**：通过 `ctx.Task` 把任务投递到全局协程池并发执行，适合 IO 密集型
- **Actor 模型**：通过 `ctx.Next` 把消息交给调度器二次分发到 Actor，适合房间类游戏

详见 [单线程模型](单线程模型.md)、[多协程模型](多协程模型.md)、[Actor模型](Actor模型.md)。

## 典型部署架构

### 单进程部署（开发/测试）

网关组件与节点组件运行在同一个进程中，便于本地调试：

```
┌──────────────┐
│    客户端     │
└──────┬───────┘
       │
┌──────▼───────┐
│  Gate + Node │  (同一容器内的多个组件)
└──────────────┘
```

### 集群部署（生产环境）


## 关键特性

### 1. 服务注册与发现

- 集群实例启动时自动注册到注册中心，并把路由/事件/服务信息写入实例元数据
- 网关通过注册中心发现可用节点
- 支持实例状态刷新与优雅下线

### 2. 用户定位

- 通过 locator（默认 Redis 实现）记录用户与网关（GID）、节点（NID）的绑定关系
- 支持跨节点消息路由，保证有状态消息准确送达

### 3. 滚动更新

- 支持不停服更新
- 网关服：进入 `Hang` 状态后拒绝新连接，等待在线会话自然退出
- 节点服：进入 `Hang` 状态后等待在途业务处理完成，绑定用户由业务决定迁移策略

详见 [滚动更新](滚动更新.md)。

### 4. 协议与运行模式

- 内置心跳与数据包协议，支持字节序、路由/序列号字节数、消息体上限等配置
- 支持 `debug` / `test` / `pre-release` / `release` 四种运行模式

## 技术栈

- **语言：** Go（`go.mod` 要求 `go 1.27.0`）
- **网络：** TCP、WebSocket、KCP、QUIC
- **编解码：** JSON、Protobuf、MsgPack、XML、YAML、TOML（`encoding` 包）
- **注册中心：** Consul、Etcd、Nacos、Polaris
- **用户定位：** Redis
- **RPC 传输：** gRPC、RPCX
- **缓存：** Redis、Memcache
- **分布式锁：** Redis、Memcache
- **事件总线：** Process、NATS、Redis、Kafka
- **日志：** Console、File、阿里云、腾讯云
- **Web 组件：** Fiber（`component/http`）

## 适用场景

- MMORPG（大型多人在线角色扮演游戏）
- MOBA（多人在线战术竞技游戏）
- 卡牌游戏
- 休闲竞技游戏
- 实时对战游戏
- 需要高并发、低延迟的实时应用

## 总结

Due v2 的架构设计充分考虑了游戏服务器的复杂性与多样性需求，通过分层架构、模块化设计与灵活并发模型，为开发者提供强大而灵活的开发框架。无论是小型独立游戏还是大型商业项目，都能找到合适的解决方案。
