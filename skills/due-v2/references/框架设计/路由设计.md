# 路由设计

## 概述

路由（Route）是消息在 Due 集群中流转的核心标识，类型为 **int32 路由号**。客户端或其他实例发送的消息携带路由号，网关据此把消息分发到注册了该路由的节点服处理。Due 通过 `RouteOptions` 支持多种路由语义：默认的**无状态路由**，以及**有状态路由**、**内部路由**、**授权路由**。

## 路由注册

节点服在启动之前（处于 `Shut` 状态）注册路由：

```go
func initApp(proxy *node.Proxy) {
    // 注册单个路由（默认无状态）
    proxy.Router().AddRouteHandler(1, loginHandler)

    // 注册带选项的路由
    proxy.Router().AddRouteHandler(2, moveHandler, node.StatefulRoute)

    // 注册路由组
    proxy.Router().Group(func(group *node.RouterGroup) {
        group.AddRouteHandler(10, chatHandler)
        group.AddRouteHandler(11, friendHandler)
    })
}

// Proxy 上也提供了便捷方法
proxy.AddRouteHandler(1, loginHandler)
proxy.RouteGroup(func(group *node.RouterGroup) { ... })
```

处理器签名：

```go
type RouteHandler func(ctx Context)
```

> 路由必须在节点服务器处于 `Shut`（未启动）状态时注册；启动后再注册会收到告警并被忽略。

节点启动时会把每个路由的 `{ID, Internal, Stateful, Authorized}` 写入注册中心（`ServiceInstance.Routes`）。网关通过服务发现获知节点注册了哪些路由，并据此分发消息。

## RouteOptions

```go
type RouteOptions struct {
    // Internal 标记内部路由：外部路由（默认）可跨客户端/网关/节点流转，
    // 内部路由只在节点之间流转。
    Internal bool
    // Stateful 标记有状态路由：无状态路由由网关按负载均衡策略分发到
    // 任意注册该路由的节点；有状态路由总是路由到用户所绑定的节点。
    Stateful bool
    // Authorized 标记授权路由：跨集群流转时必须携带 UID，否则无法投递。
    Authorized bool
    // Middlewares 是该路由的中间件链。
    Middlewares []MiddlewareHandler
}

// 预设的选项值
var (
    InternalRoute   = RouteOptions{Internal: true}
    StatefulRoute   = RouteOptions{Stateful: true}
    AuthorizedRoute = RouteOptions{Authorized: true}
)
```

> 注意：**不存在 `StatelessRoute` 常量**——不指定 `Stateful` 的路由即为无状态路由。

## 无状态路由（默认）

适用于登录验证、匹配系统、聊天服务、无状态查询等。默认即为该模式。

分发策略由网关配置 `etc.cluster.gate.dispatch`（或 `gate.WithDispatch`）决定：

| 策略 | 值 | 说明 |
|------|----|------|
| 随机 | `random` | 默认策略，从注册该路由的节点中随机选择一个 |
| 轮询 | `round-robin` | 依次轮流分发到各节点 |
| 加权轮询 | `weighted-round-robin` | 依据节点 `weight` 加权轮询 |

```toml
[cluster.gate]
    dispatch = "random"
```

分发流程：

```
客户端发送 route=1 的消息
    ↓
网关发现节点 A、B、C 都注册了 route 1
    ↓
按 dispatch 策略选择一个节点
    ↓
消息转发到该节点处理
```

## 有状态路由

适用于游戏逻辑、角色状态管理、战斗系统等需要访问用户内存数据的场景。使用 `node.StatefulRoute` 注册：

```go
proxy.AddRouteHandler(2, moveHandler, node.StatefulRoute)
```

用户登录后需要绑定网关与节点：

```go
func loginHandler(ctx node.Context) {
    // ... 鉴权逻辑，得到 uid ...

    // 绑定网关（关联用户与连接）
    if err := ctx.BindGate(uid); err != nil {
        ctx.Response(&loginRes{Code: 500})
        return
    }

    // 绑定节点（把用户绑定到当前节点；不传参数时使用当前上下文 UID）
    if err := ctx.BindNode(uid); err != nil {
        ctx.Response(&loginRes{Code: 500})
        return
    }

    ctx.Response(&loginRes{Code: 0, UID: uid})
}
```

绑定信息由 locator（默认 Redis 实现）存储。网关收到该用户的有状态路由消息时，先定位其绑定的节点，再转发过去：

```
客户端发送 StatefulRoute 消息（携带 UID）
    ↓
网关判定为有状态路由
    ↓
网关通过 locator 定位 UID 绑定的节点 NID
    ↓
转发到该节点处理（可访问该用户的内存数据）
```

> 有状态路由的定位由网关侧完成。若业务需要在节点之间主动定向投递，请使用下方「跨节点投递」。

## 跨节点投递

节点间可用 `Deliver` 定向投递消息：

```go
// 定位用户绑定的节点（按节点名区分，多为节点服实例名）
nid, err := ctx.Proxy().LocateNode(ctx.Context(), uid, "node")
if err != nil {
    return
}

err = ctx.Deliver(&cluster.DeliverArgs{
    NID: nid,   // 目标节点 ID；不设置时由系统按 UID 定位
    UID: uid,
    Message: &cluster.Message{
        Route: route,
        Data:  data,
    },
})
```

目标节点需注册对应路由；节点间流转的路由建议使用 `node.InternalRoute`。

## 路由组与中间件

中间件签名：

```go
type MiddlewareHandler func(middleware *Middleware, ctx Context)
```

`Middleware.Next(ctx)` 执行下一个中间件，`Middleware.Skip(ctx, n)` 跳过 `n` 个中间件；当中间件链执行完毕后运行最终的处理器。

```go
// 认证中间件
func authMiddleware(mw *node.Middleware, ctx node.Context) {
    if ctx.UID() == 0 {
        _ = ctx.Response(&baseRes{Code: 401})
        return // 不调用 mw.Next(ctx)，中断后续中间件与最终的路由处理器
    }
    mw.Next(ctx)
}

// 日志中间件
func logMiddleware(mw *node.Middleware, ctx node.Context) {
    log.Infof("收到消息: route=%d, uid=%d", ctx.Route(), ctx.UID())
    mw.Next(ctx)
}

// 路由组中间件
proxy.RouteGroup(func(group *node.RouterGroup) {
    group.Middleware(logMiddleware)
    group.Middleware(authMiddleware)
    group.AddRouteHandler(10, moveHandler, node.StatefulRoute)
})

// 或直接挂在单个路由上
proxy.AddRouteHandler(11, attackHandler, node.RouteOptions{
    Stateful:    true,
    Middlewares: []node.MiddlewareHandler{authMiddleware},
})
```

> 不存在 `Router.Use` 与 `ctx.Abort()`：中间件通过是否调用 `Next` 来控制是否继续向下执行。

### 默认处理器与前置/后置处理器

- `proxy.SetDefaultRouteHandler(handler)`：为所有未注册的路由提供兜底处理；`Router.HasDefaultRouteHandler()` 可判断是否已设置。
- `proxy.Router().SetPreRouteHandler(handler)`：在路由处理器之前执行。
- `proxy.Router().SetPostRouteHandler(handler)`：在路由处理器执行完成后（context 回收前）执行。

## 路由表与服务发现

节点启动时把路由表注册到服务注册中心；网关订阅节点实例列表并维护本地路由表，节点上下线会触发路由表更新：

```
节点 A 启动，注册路由 [1, 2, 10]
    ↓
网关更新路由表：route 1/2/10 → [A]

节点 B 启动，注册路由 [1, 2, 10]
    ↓
网关更新路由表：route 1/2/10 → [A, B]

节点 A 下线（或进入 Hang 状态）
    ↓
网关更新路由表：route 1/2/10 → [B]
```

可通过 `proxy.FetchNodeList(ctx, states...)` 查询满足状态的节点实例。

## 最佳实践

### 1. 合理划分路由号

```go
const (
    // 登录模块：1-99
    RouteLogin  int32 = 1
    RouteLogout int32 = 2

    // 匹配模块：100-199
    RouteMatchStart  int32 = 100
    RouteMatchCancel int32 = 101

    // 游戏模块：1000-1999
    RouteMove   int32 = 1000
    RouteAttack int32 = 1001
    RouteSkill  int32 = 1002
)
```

### 2. 集中管理路由号

```go
// routes/routes.go
package routes

const (
    Login  int32 = 1
    Logout int32 = 2
    Move   int32 = 1000
    Attack int32 = 1001
)

// 路由号到名称的映射（便于调试）
var RouteNames = map[int32]string{
    Login:  "Login",
    Logout: "Logout",
    Move:   "Move",
    Attack: "Attack",
}
```

### 3. 避免在路由处理器中阻塞耗时操作

单线程模型下，阻塞会卡住当前节点的分发协程。可将耗时逻辑投递到协程池或异步执行：

```go
func heavyHandler(ctx node.Context) {
    // 推荐：Task 会把任务投递到全局协程池
    ctx.Task(func(ctx node.Context) {
        result := heavyComputation()
        _ = ctx.Response(result)
    })
}
```

详见 [单线程模型](单线程模型.md)、[多协程模型](多协程模型.md)。

## 常见问题

### Q1：如何知道一个路由号注册在哪些节点服？

**A：** 查询注册中心中节点实例的 `Routes` 字段，或使用 `proxy.FetchNodeList(ctx, cluster.Work)`。

### Q2：有状态路由的用户绑定信息丢失怎么办？

**A：** 绑定信息存于 locator（Redis）。数据丢失后，用户需要重新登录并绑定节点。

### Q3：能否动态添加或删除路由？

**A：** 路由需在节点 `Shut`（未启动）状态注册；运行期注册会被忽略并告警。需要变更路由时应通过节点滚动更新完成。

### Q4：路由号有数量限制吗？

**A：** 取决于 `routeBytes` 配置（有符号整数）：1 字节为 -128 ~ 127，2 字节为 -32768 ~ 32767，4 字节为 int32 范围。

## 总结

路由设计是 Due 分布式架构的核心。通过无状态路由、有状态路由、内部路由与授权路由的组合，可以构建高性能、可扩展的游戏服务器。理解路由注册、分发策略与中间件机制，是开发复杂游戏逻辑的基础。
