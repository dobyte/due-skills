# 架构设计

## 1. 分层与角色

按**角色**切分进程，不按业务切分。一个角色一类进程，职责单一、可独立扩缩容。

| 层次 | 职责 | 组件 | 典型服务 |
| --- | --- | --- | --- |
| 接入层 | 客户端长连接、协议编解码、HTTP 入口 | Gate、HTTP | `gate`、`web`、`admin` |
| 业务层 | 有状态业务、Actor 编排、会话状态 | Node | `hall`、`game-*`、`activity` |
| 服务层 | 无状态微服务、跨节点调用 | Mesh | `mesh`（宿主多个 domain） |

- **标准起步集**：`gate` + `hall` + `mesh` + `web` + 顶层 `internal/`。
- 接入层不承载业务；业务层不持有他人数据；服务层无状态、可随时重启。

## 2. 进程 = 单一集群类型

进程的集群类型是**单一** `cluster.Kind`（Gate / Node / Mesh / …），由加入容器的组件决定。一个进程只承担一种角色。

- 不要让一个进程同时兼任多种角色（例如把 Gate 与 Node 塞进同一进程）——这会让扩缩容、滚动升级、定位逻辑全部复杂化。
- 开发期想减少外部依赖（Redis / 注册中心），应通过**配置**降低依赖强度，而不是让进程兼任角色。

## 3. internal/ 内核职责

`internal/` 是跨服务共享内核，服务一拆就必然共享，因此**第一天就建立**。

| 目录 | 职责 |
| --- | --- |
| `code/` | 统一错误码（包装协议层的错误码枚举） |
| `protocol/` | 协议源（`.proto`）与生成物 |
| `define/` | 常量，含路由号段登记 |
| `component/<x>/` | 公共组件单例 |
| `event/<domain>/` | 事件 topic 与载荷 |
| `model/` `dao/<domain>/` | 数据模型与数据访问 |
| `service/<domain>/{pb,server,client}` | 微服务三件套 |
| `middleware/` | 中间件 |
| `helper/` `library/` `utils/` | 工具 |

内核**不得反向依赖具体业务服务目录**（如不得 import `hall/...`）。

## 4. 服务边界

- 按角色切（接入 / 业务 / 服务），业务内部再按**水平领域**拆（如 `hall`、`activity`、各子游戏）。
- 子游戏是独立 Node 服务，各自继承协议号段。
- 新领域优先新增 Mesh domain，而不是把逻辑塞进已有服务。

## 5. 跨服务调用链路

```
客户端 ──WS──> gate ──(定位 + RPC)──> node(hall / game-* / activity)
HTTP    ──HTTP─> web/admin ──(Mesh client, discovery://<domain>)──> mesh
node/mesh ──事件总线──> 其它节点/服务          # 异步解耦
node/mesh ──缓存/分布式锁──> 共享状态/互斥
```

- **业务层调用服务层**：统一 `internal/service/<domain>/client` → `discovery://<domain>`。
- **服务注册**：`internal/service/<domain>/server` 在 `Init()` 中注册服务提供者。
- **禁止**：业务层直连他人数据库 / Redis；跨服务绕过 Mesh 私有通道。

## 6. 反模式

- 一个进程兼任多种角色。
- 业务逻辑写在 `main.go` 或 `internal/`（内核不该有业务）。
- 跨服务直连他人存储。
- `internal/` 反向依赖业务服务目录。
- 把"无状态"服务做成有状态（破坏了水平扩展的前提）。
